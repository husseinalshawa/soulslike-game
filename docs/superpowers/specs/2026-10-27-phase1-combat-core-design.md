# مواصفة التصميم — لعبة سولز عالم مفتوح: المرحلة 0 (التأسيس) + المرحلة 1 (جوهر القتال)

**التاريخ:** 2026-10-27
**الحالة:** بانتظار مراجعة الشريك
**الاسم المؤقت للمشروع:** soulslike-game (قابل للتغيير لاحقاً)

---

## 1. الرؤية العامة

لعبة سولز (Souls-like) بعالم مفتوح مستوحاة من Elden Ring في فلسفة التصميم وطريقة اللعب:
قتال حذر قائم على الستامينا والتفادي، أعداء وبوسات صعبة لكن عادلة، استكشاف حر،
مواقع راحة، فقدان الأرواح عند الموت واستعادتها، وقصة غامضة تُروى بأسلوب غير مباشر.

- **المحرك:** Unity 6 (أحدث LTS) مع Universal Render Pipeline (URP).
- **اللغة:** C#.
- **الستايل الفني المستهدف:** منمنم قاتم (stylized dark fantasy) — الأجواء عبر الإضاءة
  والضباب والألوان، وليس الواقعية.
- **المنصة المستهدفة أولاً:** حاسب شخصي (Windows)، بدعم يد تحكم وكيبورد/ماوس من اليوم الأول.
- **المطوّر:** شخص واحد لديه خلفية برمجية وجديد على Unity، بمساعدة Claude.

### خارطة الطريق المعتمدة

| المرحلة | المحتوى | النتيجة القابلة للعب |
|---------|---------|----------------------|
| 0 — التأسيس | مشروع Unity 6 + URP، نظام الإدخال، Cinemachine، Git | مشروع جاهز للعمل |
| **1 — جوهر القتال (هذه المواصفة)** | تحكم، كاميرا + lock-on، ستامينا، قتال، عدو بذكاء اصطناعي، موت | ساحة اختبار بقتال سولز حقيقي |
| 2 — حلقة السولز | مواقع راحة، إسقاط/استعادة الأرواح، رفع المستوى، أول بوس | حلقة اللعب الكاملة |
| 3 — العالم المفتوح الأول | منطقة مفتوحة، الستايل الفني، الحصان | أول منطقة استكشاف |
| 4 — العمق | أسلحة متنوعة، سحر وقدرات، تجهيزات | تنوع أساليب اللعب |
| 5 — القصة والعالم | NPCs، مهام، قصة غامضة، مناطق إضافية | لعبة متكاملة |

كل مرحلة لها مواصفة وخطة تنفيذ منفصلة تُعتمدان قبل البدء. هذه المواصفة تغطي
المرحلتين 0 و1 فقط.

### معيار نجاح المرحلة 1

ساحة اختبار رمادية يستطيع اللاعب فيها: التحرك والعدو، قفل الكاميرا على عدو،
تنفيذ ضربات خفيفة وثقيلة وتفادي بحصانة وصد، إدارة الستامينا، وقتال عدو واحد
يهاجم بهجمات مقروءة — والموت وإعادة المحاولة. **المقياس الحاسم: هل القتال ممتع
ومُرضٍ؟** إذا لا، نعدّل هنا قبل أي مرحلة تالية.

## 2. المرحلة 0 — التأسيس التقني

### القرارات

- **Unity 6 LTS + URP:** الـ URP يوفر الإضاءة والضباب الحجمي والـ post-processing
  (Vignette، Color Grading، Bloom) المطلوبة لأجواء السولز، مع أداء جيد لعالم مفتوح.
- **Input System (الجديد):** خريطة إدخال واحدة (Action Map) تدعم يد التحكم
  والكيبورد/الماوس معاً. أزرار افتراضية على نمط Elden Ring (التفادي على B/Space،
  الضرب على RB/زر فأرة أيسر... تُضبط بالتفصيل في خطة التنفيذ).
- **Cinemachine:** لكاميرا الشخص الثالث والـ lock-on.
- **Git:** مستودع مع `.gitignore` قياسي لـ Unity (استبعاد Library وTemp وLogs...).
  ملفات المشاهد والـ prefabs تُحفظ كنص (Force Text) لتسهيل المراجعة.

### هيكل المشروع

```
Assets/
  _Game/                  # كل ما نكتبه نحن — معزول عن الأصول الخارجية
    Scripts/
      Player/             # التحكم، آلة الحالات، الكاميرا
      Combat/             # Health, Stamina, Poise, Hitbox/Hurtbox, Damage
      Enemies/            # ذكاء الأعداء
      Data/               # تعريفات ScriptableObject (أسلحة، إحصائيات)
      Core/               # أدوات مشتركة (مؤقتات، أحداث...)
      UI/                 # أشرطة الصحة والستامينا، شاشة الموت
    Scenes/               # ساحة الاختبار
    Prefabs/
    Data/                 # ملفات البيانات الفعلية (.asset)
    Art/                  # مؤقت حالياً
  ThirdParty/             # أصول خارجية (أنيميشنات مجانية...)
```

## 3. المرحلة 1 — البنية المعمارية

### المبدأ المركزي: الالتزام بالحركة (Action Commitment)

إحساس السولز يأتي من أن كل فعل التزام: بدأتَ ضربة ثقيلة؟ أنت ملتزم بها حتى
نافذة الإلغاء المحددة. هذا يُنفَّذ عبر **آلة حالات (State Machine)** صريحة
للاعب، كل حالة تملك قرار الدخول والخروج.

### حالات اللاعب

| الحالة | الوصف | الخروج منها |
|--------|-------|-------------|
| Locomotion | وقوف/مشي/جري/عدو | في أي وقت لأي حالة أخرى |
| Dodge | تدحرج بمسافة ثابتة مع i-frames | بعد انتهاء الأنيميشن، أو إلغاء متأخر إلى هجوم |
| Attack | ضربة خفيفة/ثقيلة من كومبو | نافذة إلغاء محددة بحدث أنيميشن (إلى تفادي أو الضربة التالية) |
| Block | رفع الدرع، حركة بطيئة | إفلات الزر، أو كسر الحرس عند نفاد الستامينا |
| Stagger | تلقي ضربة كسرت الـ poise — فقدان سيطرة مؤقت | انتهاء الأنيميشن |
| Death | الموت | إعادة الظهور |

تُبنى الآلة ككلاسات C# صريحة (حالة = كلاس)، وليست مبنية على Animator فقط —
الـ Animator ينفّذ العرض، والمنطق ملكنا، حتى نستطيع لاحقاً إضافة حالات
(ركوب الحصان، التعاويذ) بدون إعادة بناء.

### مكونات القتال المشتركة (يستخدمها اللاعب والأعداء بالتساوي)

- **Health:** نقاط حياة، استقبال ضرر، حدث عند الموت.
- **Stamina:** استهلاك (هجوم/تفادي/عدو/صد ناجح)، تجدد بعد مهلة قصيرة من آخر
  استهلاك، وتجدد أبطأ أثناء رفع الدرع. ستامينا غير كافية = الفعل مرفوض.
- **Poise (التوازن):** كل ضربة تُلحق ضرر poise؛ عند تجاوز العتبة يدخل المستقبِل
  حالة Stagger. يتجدد مع الوقت.
- **Hitbox/Hurtbox:** الـ Hitbox (صندوق الضرر على السلاح) يُفعَّل ويُعطَّل عبر
  **أحداث الأنيميشن** — الضربة تصيب فقط أثناء مسار السلاح الفعلي. الـ Hurtbox
  (جسم المستقبِل) يستقبل ويمرر الضرر إلى Health/Poise. ضربة واحدة لا تصيب
  نفس الهدف مرتين.
- **Damage:** حزمة الضرر (قيمة HP، قيمة poise، اتجاه المصدر) تنتقل ككائن واحد
  من الـ Hitbox إلى الـ Hurtbox.

### البيانات في ScriptableObjects

- **WeaponData:** ضرر خفيف/ثقيل، ضرر poise، استهلاك ستامينا لكل ضربة، عدد
  ضربات الكومبو، سرعة.
- **CharacterStats:** صحة قصوى، ستامينا قصوى، poise، سرعات الحركة.

تعديل التوازن = تعديل ملف بيانات، بدون لمس الكود. هذا الأساس الذي يُبنى عليه
نظام الأسلحة المتنوعة في المرحلة 4 وإحصائيات رفع المستوى في المرحلة 2.

### الكاميرا والـ Lock-on

- كاميرا شخص ثالث حرة (Cinemachine) تدور بالماوس/العصا اليمنى.
- **Lock-on:** زر يقفل على أقرب هدف في مجال الرؤية؛ الكاميرا تؤطّر اللاعب
  والهدف معاً؛ حركة اللاعب تصبح strafe (يواجه الهدف دائماً)؛ تحريك العصا
  اليمنى يميناً/يساراً يبدّل الهدف؛ يفك القفل بموت الهدف أو تجاوز مسافة قصوى
  أو ضغط الزر مجدداً.

### العدو (نمط السولز الأساسي)

آلة حالات بسيطة: **دورية → اكتشاف (مسافة + مجال رؤية) → اقتراب → هجوم → استراحة**.

- الهجمات **مُعلَنة مسبقاً (telegraphed):** وضعية تحضير واضحة قبل الضربة تعطي
  اللاعب وقتاً للقراءة والرد.
- بعد كل هجوم **نافذة استراحة (recovery)** هي فرصة اللاعب للعقاب — هذا جوهر
  إيقاع قتال السولز.
- العدو يستخدم نفس مكونات Health/Stamina/Poise/Hitbox — يمكن كسر توازنه
  وعقابه.
- عدو واحد فقط في هذه المرحلة (مقاتل سيف بسيط). التنويع لاحقاً.

### الموت وواجهة المستخدم

- صحة اللاعب تصل صفراً → حالة Death → شاشة "YOU DIED" (أو مكافئ عربي نقرره
  لاحقاً) → إعادة الظهور عند نقطة البداية، والعدو يُعاد ضبطه.
- UI المرحلة 1: شريط صحة وشريط ستامينا للاعب، شريط صحة صغير فوق العدو عند
  الـ lock-on، شاشة الموت. لا قوائم ولا جرد (inventory) في هذه المرحلة.

### الأصول المؤقتة

- ساحة اختبار رمادية (أرضية، بضعة جدران وصناديق للاختباء).
- شخصية وأنيميشنات مجانية: Unity Starter Assets أو Mixamo (مشي/جري/تدحرج/
  ضربات/صد/موت). الجودة البصرية ليست هدفاً الآن.

## 4. تدفق البيانات (مثال: ضربة خفيفة تصيب العدو)

1. الإدخال → آلة حالات اللاعب تتحقق: الحالة تسمح؟ الستامينا تكفي؟
2. دخول حالة Attack → خصم الستامينا → تشغيل الأنيميشن.
3. حدث أنيميشن "OpenHitbox" → تفعيل Hitbox السلاح بحزمة ضرر من WeaponData.
4. تلامس مع Hurtbox العدو → تمرير الحزمة → Health يخصم، Poise يخصم.
5. تجاوز عتبة poise؟ → العدو يدخل Stagger. الصحة صفر؟ → العدو يموت.
6. حدث أنيميشن "CloseHitbox" → تعطيل الـ Hitbox. نافذة الإلغاء تفتح → اللاعب
   يستطيع متابعة الكومبو أو التفادي.

## 5. معالجة الأخطاء والحالات الحدية

- إدخال أثناء حالة لا تسمح به → يُتجاهل (مع إدخال مخزّن input buffering للضربة
  التالية فقط، نافذة قصيرة ~0.2 ثانية — ضروري لإحساس استجابة سولز صحيح).
- ستامينا غير كافية → الفعل يُرفض، ومؤشر بصري على الشريط.
- ضربة أثناء i-frames للتفادي → لا ضرر إطلاقاً.
- صد ناجح → الضرر يُلغى أو يُخفَّض، تُخصم ستامينا من الصادّ؛ نفدت ستامينا
  الصادّ → كسر حرس (Stagger).
- موت العدو أثناء lock-on → فك القفل تلقائياً.

## 6. الاختبار

- **اختبارات آلية (EditMode)** لمنطق الأرقام الخالص: استهلاك/تجدد الستامينا،
  حساب الضرر، عتبات poise، شروط انتقالات آلة الحالات. المنطق يُكتب منفصلاً عن
  MonoBehaviour قدر الإمكان ليكون قابلاً للاختبار.
- **قائمة فحص يدوية لإحساس اللعب** (لا تقيسها الاختبارات الآلية): هل التفادي
  مُرضٍ وواضح التوقيت؟ هل للضربات وزن؟ هل هجمات العدو قابلة للقراءة؟ هل القتال
  "عادل لكن صعب"؟
- أرقام التوازن الأولية (صحة، ضرر، ستامينا) تخمينية وتُضبط بالتجربة — لهذا هي
  في ScriptableObjects.
